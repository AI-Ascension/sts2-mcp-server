# ADR 0027: watchdog-recovery MCP sideband

- Status: Accepted for the bounded read/reconcile MCP consumer seam
- Date: 2026-09-20
- Owner: `sts2-mcp-server`
- Contracts: `sts2-protocol/watchdog-recovery-v1` and the gateway-owned
  `/v1/recovery/operation/{lookup,reconcile}` sideband routes

## Context

The durable watchdog recovery profile records an operation intent before it dispatches a host
effect, so a lost dispatch answer must be resolved against the authoritative gateway record rather
than repeated. The recovery contract defines that record, the frame that carries it, and the two
gateway routes that read and reconcile it, but it does not define MCP tools or transport
authentication for this consumer.

Before this decision the MCP executable had no recovery mapping at all. A recovery episode that
reached the reconcile path called `watchdog.operation_lookup` against an MCP child whose catalog
did not carry it, so the call failed at the MCP boundary and the episode ended unrecovered even
though the gateway held a resolvable record. The MCP consumer needs a narrow profile that owns the
two-route sideband and nothing else, and that cannot turn a recovery read into a second effect
attempt.

## Decision

The opt-in `watchdog-recovery-v1` profile advertises a nine-tool watchdog surface in fixed order:
`watchdog.bootstrap`, `host_fence`, `lease_acquire`, `lease_renew`, `lease_revoke`,
`operation_intent`, `operation_dispatch`, `operation_lookup`, and `operation_reconcile`. The first
seven are advertised for contract shape only: this sideband profile carries neither the durable
boot nor the dispatch routes, so a call to one is refused with a typed
`watchdog_recovery_route_not_installed` tool error instead of being forwarded anywhere.

Only the two recovery reads are wired, each to one fixed gateway route:

| Tool | Fixed route | Capability |
| --- | --- | --- |
| `watchdog.operation_lookup` | `POST /v1/recovery/operation/lookup` | `recovery_read` |
| `watchdog.operation_reconcile` | `POST /v1/recovery/operation/reconcile` | `recovery_reconcile` |

Each MCP argument is a closed `{mcp_session_id, payload}` wrapper. The session must equal the active
MCP session, and the payload is the caller's own recovery reference: `{operation, lookup_scope:
"historical_read"}` for lookup, and `{operation, strategy, current_fence}` for reconcile. The MCP
adapter validates the reference shape, the closed nine-field envelope, the pinned contract and
schema digest, direction, the actor/auth principal and role, the per-operation capability, and the
result, witness, and original-context members, but it never rewrites or re-derives any field of the
reference or of the returned operation record.

The request frame is generated by the process itself. Its principal is the configured
`STS2_CALLER_ID`, which the profile requires to be a UUID v4, and it is never taken from a tool
argument; the correlation identifier it carries must be echoed by the response. Lookup never
authorizes a mutation and never replays a host effect, and reconcile resolves an uncertain
operation against the authoritative record without replaying the original action.

The gateway response is surfaced verbatim as the tool result. Because the runtime owner, not MCP,
retains the durable intent that a surfaced record must be cross-checked against, projecting or
re-summarizing that record here would destroy the evidence the caller needs. The adapter binds the
response to the exchange, rejects a body that is not a closed recovery response, and passes the
accepted frame through unchanged. One accepted frame is bounded at 256 KiB.

The executable uses the trusted `STS2_RECOVERY_TOKEN` and the fixed
`x-sts2-recovery-capability` value for the route, alongside the configured MCP session and
correlation headers. A gateway answer that is a bare `{"error_code": …}` short-circuit body is
reported as `watchdog_recovery_frame_invalid` rather than passed through as a frame.

## Compatibility and evidence

The profile is additive and does not change existing catalogs, routes, or bounds. The installed
recovery frame schema digest is pinned as
`fb934d3157485aaf6e13e6ebbb213ec8a14c7fc6f5eeebc06b7a22c1f0009217`, and the sideband revision
identifier is `watchdog-recovery-v1-mcp`. A recovery-routed exchange bypasses the instance-prefixed
admission path and the shared response classifier so that a `503` carrying an unresolved
`MAY_HAVE_BEEN_DISPATCHED` frame reaches the caller as that frame instead of being flattened to a
generic unavailable error.

Artifact, validation, serialized MCP mapping, and loopback HTTP tests establish source/component
behavior at the MCP boundary only. The following claims remain unverified and must not be inferred
from this decision: duplicate-JSON-key rejection is not implemented in the MCP frame validator, so
a duplicated envelope member is folded rather than refused; gateway persistence of the operation
record; the existence or behavior of a native restore adapter; the recovery-control host routes
that would let a real gateway settle an unresolved operation; and deployment or release support.
No independent review was obtained for this change: a single author identity owns the change, and
the subagents an independent review would require were unavailable, so the accompanying review is
a labelled self-review at the exact head.
